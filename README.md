# LifePass

## 청년센터·지자체를 위한 복지 사각지대 관리 AI Agent 플랫폼

LifePass는 청년 개인이 혼자 쓰는 단순 복지 추천 앱이 아니라, **청년센터, 지자체, 대학, 복지기관, 고용지원기관이 여러 청년의 복지 사각지대와 신청 타이밍을 관리하도록 돕는 기관용 AI 복지 운영 플랫폼**입니다.

최종 수혜자는 실업 청년, 청년 1인가구, 저소득 청년, 프리랜서, 월세 부담이 큰 청년입니다.  
하지만 실제 도입 고객은 이들을 상담하고 지원해야 하는 **복지기관과 자치단체**입니다.

LifePass는 기관이 보유한 청년 상담 데이터, CSV 명단, 정책 데이터, 신청 상태 정보를 바탕으로 다음 흐름을 지원합니다.

- 여러 청년의 상황 정보를 한 번에 입력합니다.
- 각 청년이 받을 수 있는 복지·고용·정책금융 제도를 판정합니다.
- 실업급여 종료, 소득 변화, 월세 변화, 이사 같은 생애전환 상황을 계산합니다.
- 복지절벽 위험이 큰 청년을 먼저 찾습니다.
- 상담사가 우선 검토해야 할 대상을 선별합니다.
- 신청 서류, 신청 마감, 알림, 검토 상태를 관리합니다.
- 정책 변경이 여러 청년에게 어떤 영향을 주는지 미리 계산합니다.
- 개인정보 접근 기록과 감사 로그를 남깁니다.

> 중요한 원칙: LifePass는 LLM이 자격 여부를 마음대로 판단하지 않습니다.  
> 실제 자격 판정은 `core/rule_engine.py`의 규칙 기반 판정 코드가 수행하고, LLM은 판정 결과와 정책 근거를 사람이 이해하기 쉽게 설명하는 보조 역할만 합니다.

## 1. 이 프로젝트가 해결하려는 문제

복지 사각지대는 혜택이 없어서만 생기지 않습니다. 실제 현장에서는 다음과 같은 이유로 지원이 필요한 청년이 제도를 놓치는 경우가 많습니다.

- 청년 본인이 어떤 제도가 있는지 모릅니다.
- 정책 조건이 복잡해서 상담사도 빠르게 판단하기 어렵습니다.
- 실업급여 종료, 취업, 소득 증가, 이사 이후 받을 수 있는 제도가 달라집니다.
- 신청 마감일과 준비 서류를 놓칩니다.
- 여러 혜택 중 동시에 받을 수 없는 제도가 있습니다.
- 정책이 바뀌었을 때 기존 상담 대상자 중 누가 새로 지원 가능한지 파악하기 어렵습니다.
- 기관은 여러 청년을 관리해야 하지만, 상담 기록과 신청 진행 상태가 흩어져 있습니다.

LifePass는 이 문제를 다음 흐름으로 해결합니다.

```text
청년 데이터 입력
→ 프로필 구조화
→ 복지 자격 판정
→ 혜택 조합 정리
→ 복지절벽 위험 예측
→ 상담 우선순위 산출
→ 신청 관리
→ 알림 생성
→ 감사 로그 저장
```

즉, LifePass는 “혜택 목록을 보여주는 앱”이 아니라, **기관이 여러 청년의 복지 지원 과정을 운영하는 플랫폼**입니다.

## 2. 대상 고객과 최종 수혜자

### 2.1 도입 고객

LifePass의 주요 도입 고객은 다음과 같습니다.

- 지자체 청년정책 부서
- 청년센터
- 고용복지플러스센터
- 대학 취업지원센터
- 대학 학생복지팀
- 사회복지기관
- 비영리 청년 지원 단체
- 금융복지 상담기관
- 지역 복지재단
- 공공기관 청년지원 사업팀

이 기관들은 한 명의 청년만 보는 것이 아니라, 여러 명의 청년을 지속적으로 관리해야 합니다.  
그래서 CSV 일괄분석, DB 저장, 운영자 검토, 알림, 개인정보 감사 로그 같은 기능이 필요합니다.

### 2.2 최종 수혜자

LifePass의 최종 수혜자는 다음과 같은 청년 개인입니다.

- 실업급여 종료를 앞둔 청년
- 청년 1인가구
- 프리랜서
- 저소득 근로자
- 월세 부담이 큰 청년
- 취업 준비생
- 아르바이트 또는 단기 근로자
- 소득 변화로 복지 자격이 달라질 수 있는 청년

즉, LifePass는 **기관이 사용하는 플랫폼**이지만, 실제 혜택을 받는 사람은 청년 개인입니다.

## 3. 제품 포지셔닝

LifePass는 B2B2C 구조의 복지 운영 플랫폼입니다.

```text
B2B2C 구조

복지기관·지자체·청년센터·대학
→ LifePass를 사용해 청년 데이터를 관리
→ 청년 개인에게 맞춤형 복지 안내와 신청 지원 제공
```

개인용 복지 추천 앱과의 차이는 다음과 같습니다.

| 구분 | 개인용 복지 추천 앱 | LifePass |
|---|---|---|
| 주 사용자 | 청년 개인 | 기관 상담사, 운영자, 정책 담당자 |
| 분석 대상 | 한 명 | 여러 명 |
| 데이터 입력 | 직접 입력 | 직접 입력 + CSV + 정책 데이터 |
| 주요 목적 | 내 혜택 확인 | 복지 사각지대 발굴과 신청 관리 |
| DB 필요성 | 낮음 | 높음 |
| 이벤트/알림 | 개인 리마인더 수준 | 여러 청년의 상태 변화 추적 |
| 감사 로그 | 거의 불필요 | 개인정보 접근 기록 필요 |
| 정책 변경 분석 | 불필요 | 영향받는 청년과 예산 변화 분석 필요 |

LifePass는 개인이 혼자 쓰는 복잡한 시스템이 아니라, **기관이 여러 청년을 놓치지 않고 지원하기 위한 운영 도구**입니다.

## 4. 핵심 사용 시나리오

### 4.1 청년센터 상담사 시나리오

청년센터 상담사가 상담 대상자 300명의 기본 정보를 CSV로 업로드합니다.

LifePass는 각 청년에 대해 다음을 자동으로 계산합니다.

- 현재 받을 수 있는 복지 혜택
- 실업급여 종료 예정자
- 월세 지원 가능성이 높은 대상자
- 신청 마감이 임박한 대상자
- 소득 변화 시 혜택이 사라질 위험이 있는 대상자
- 상담사가 우선 검토해야 할 고위험 대상자

상담사는 전체 명단 중 누구를 먼저 도와야 하는지 빠르게 파악할 수 있습니다.

### 4.2 지자체 정책 담당자 시나리오

지자체가 청년 월세 지원 정책의 나이 기준을 바꾸려고 합니다.

예를 들어 기존 기준이 다음과 같다고 가정합니다.

```text
기존: 만 19세 이상 34세 이하
변경안: 만 19세 이상 39세 이하
```

LifePass는 정책 변경 전후를 비교해 다음을 계산합니다.

- 새로 지원 가능해지는 청년 수
- 기존 대상자 중 지원금이 바뀌는 사람 수
- 월 예산 변화
- 연 예산 변화
- 영향을 받는 사용자 목록
- 정책 변경으로 생기는 복지 사각지대 감소 효과

이 기능은 `core/v5_policy_digital_twin.py`에서 담당합니다.

### 4.3 대학 취업지원센터 시나리오

대학 취업지원센터가 졸업예정자, 휴학생, 취업준비생 명단을 입력합니다.

LifePass는 다음 정보를 제공합니다.

- 취업 준비 중 받을 수 있는 청년 지원 제도
- 구직활동 지원 대상 여부
- 월세 지원 가능 여부
- 소득 발생 이후 사라질 수 있는 혜택
- 신청 마감 전 알림 대상자
- 상담 필요 우선순위

대학은 학생 개개인에게 흩어진 정보를 수동으로 안내하는 대신, 데이터 기반으로 지원 우선순위를 정할 수 있습니다.

## 5. 전체 처리 흐름

LifePass는 외부 데이터와 사용자 데이터를 다음 순서로 처리합니다.

```text
1. 기관이 청년 데이터를 입력합니다.
   - 화면 직접 입력
   - 자연어 입력
   - CSV 일괄 업로드

2. 시스템이 사용자 정보를 구조화합니다.
   - 나이
   - 지역
   - 가구원 수
   - 월소득
   - 월세
   - 고용 상태
   - 실업급여 잔여일

3. 정책 데이터를 불러옵니다.
   - 기본 정책 카탈로그
   - CSV 정책 피드
   - 공공 API 연동 구조
   - 샘플 fallback 데이터

4. 룰엔진이 자격을 판정합니다.
   - 나이 조건
   - 지역 조건
   - 소득 조건
   - 가구 조건
   - 고용 상태 조건

5. 최적화기가 혜택 조합을 정리합니다.
   - 동시에 받을 수 없는 혜택 제거
   - 월 환산효과 계산
   - 신청 우선순위 산출

6. 시뮬레이터가 미래 변화를 계산합니다.
   - 3개월 뒤
   - 6개월 뒤
   - 12개월 뒤
   - 실업급여 종료 이후
   - 소득 발생 이후

7. RAG와 LLM이 설명을 만듭니다.
   - 정책 근거 검색
   - 판정 결과 요약
   - 신청 준비 안내

8. 운영 기능으로 연결합니다.
   - 신청 case 생성
   - 상담사 검토
   - 알림 outbox
   - 개인정보 접근 로그
   - 감사 기록 저장
```

## 6. 외부 데이터 입력 방식

LifePass는 크게 세 종류의 외부 데이터를 입력받습니다.

### 6.1 청년 프로필 CSV

기관이 보유한 상담 대상자 명단을 CSV로 입력할 수 있습니다.

예시:

```csv
name,age,region,household_size,monthly_income,rent,employment_status,unemployment_benefit_days_left
kim,27,서울,1,0,550000,unemployed,45
lee,31,경기,1,1200000,450000,part_time,0
park,24,부산,2,800000,300000,student,0
```

LifePass는 각 행을 한 명의 청년 프로필로 바꿉니다.

```text
CSV 1행 → 청년 1명
CSV 2행 → 청년 1명
CSV 3행 → 청년 1명
```

그 후 각 청년에 대해 자격 판정, 혜택 추천, 복지절벽 위험 분석을 수행합니다.

### 6.2 정책 CSV

기관이나 운영자가 정책 데이터를 CSV로 입력할 수 있습니다.

예시:

```csv
policy_id,name,region,age_min,age_max,income_max,monthly_value,source_url,valid_from,valid_to
p001,서울 청년 월세 지원,서울,19,34,2000000,200000,https://example.go.kr/p001,2026-01-01,2026-12-31
p002,청년 구직활동 지원,전국,18,34,1800000,500000,https://example.go.kr/p002,2026-03-01,2026-11-30
```

처리 과정은 다음과 같습니다.

```text
정책 CSV 업로드
→ 정책 항목 추출
→ 내부 정책 형식으로 변환
→ 출처와 수집 시각 저장
→ 기존 정책과 비교
→ 변경 이력 저장
→ 자격 판정에 반영
```

### 6.3 공공 정책 API

실서비스에서는 복지로, 정부24, 고용24, 지자체 공고 API 같은 공공 정책 데이터를 연결할 수 있습니다.

관련 파일은 다음과 같습니다.

```text
core/public_api_clients.py
core/policy_ingestion.py
core/policy_provenance.py
core/policy_store.py
```

처리 흐름:

```text
공공 API 호출
→ 정책 JSON 또는 XML 응답 수신
→ 필요한 항목 추출
→ LifePass 내부 정책 형식으로 변환
→ 정책 출처와 원문 링크 저장
→ 정책 변경 전후 diff 저장
→ 사용자 판정과 RAG 검색에 활용
```

API 키가 없는 환경에서도 시연할 수 있도록 샘플 fallback 구조를 포함합니다.

## 7. 주요 기능

### 7.1 자연어 온보딩

상담사는 청년의 상황을 자연어로 입력할 수 있습니다.

예시:

```text
서울에 사는 27세 1인가구이고, 월소득은 없고, 월세는 55만 원입니다.
실업급여는 45일 남았습니다.
```

`core/profile_parser.py`는 이 문장을 다음과 같은 구조화된 값으로 바꿉니다.

```text
나이: 27
지역: 서울
가구원 수: 1
월소득: 0
월세: 550000
실업급여 잔여일: 45
```

### 7.2 규칙 기반 자격 판정

복지 자격은 LLM이 직접 판단하지 않습니다.  
정책 조건은 `data/benefits.json` 또는 정책 DB에 저장되고, `core/rule_engine.py`가 조건을 하나씩 확인합니다.

예를 들어 다음 조건을 검사합니다.

- 나이가 기준에 맞는가?
- 지역이 기준에 맞는가?
- 월소득이 기준 이하인가?
- 가구원 수가 맞는가?
- 실업급여 수급 여부가 조건에 맞는가?

이 방식은 같은 입력이면 같은 결과가 나오기 때문에, 기관 상담과 감사에 적합합니다.

### 7.3 혜택 조합 최적화

받을 수 있는 혜택이 여러 개라고 해서 모두 동시에 받을 수 있는 것은 아닙니다.

`core/optimizer.py`와 `core/constraint_solver.py`는 다음을 계산합니다.

- 같이 받을 수 없는 혜택 제거
- 월 환산효과가 큰 조합 선택
- 신청 난이도와 긴급도 고려
- 상담사가 먼저 안내해야 할 혜택 추천

즉, 단순 목록이 아니라 **실제 신청 가능한 조합**을 제공합니다.

### 7.4 생애전환·복지절벽 시뮬레이션

LifePass의 핵심 기능 중 하나입니다.

현재 상태뿐 아니라 앞으로의 변화를 계산합니다.

예시 상황:

- 실업급여가 45일 뒤 끝남
- 3개월 뒤 아르바이트 시작
- 월소득이 0원에서 80만 원으로 증가
- 6개월 뒤 월소득이 140만 원으로 증가
- 이사로 월세가 바뀜

LifePass는 각 시점에서 받을 수 있는 제도가 어떻게 달라지는지 계산합니다.

```text
현재
→ 3개월 뒤
→ 6개월 뒤
→ 12개월 뒤
```

이를 통해 소득은 늘었지만 혜택이 사라져 실제 생활 여건이 나빠지는 **복지절벽 위험**을 찾을 수 있습니다.

### 7.5 CSV 일괄분석

기관용 플랫폼으로서 가장 중요한 기능 중 하나입니다.

청년센터나 지자체는 여러 청년의 정보를 한 번에 입력해야 합니다.  
LifePass는 CSV 파일을 받아 각 청년을 자동 분석합니다.

결과 예시:

```text
전체 대상자: 300명
현재 신청 가능자: 184명
복지절벽 위험군: 37명
실업급여 30일 이내 종료 예정자: 22명
상담사 검토 필요 사례: 15명
신청 마감 임박자: 19명
```

이 기능을 통해 기관은 한정된 상담 인력으로도 우선순위를 정할 수 있습니다.

### 7.6 정책 수집과 변경 이력 관리

정책은 자주 바뀝니다.  
그래서 LifePass는 정책 데이터의 출처와 변경 이력을 남기는 구조를 갖습니다.

관리 항목:

- 정책 이름
- 정책 조건
- 지원 금액
- 신청 기간
- 원문 링크
- 수집 시각
- 출처 기관
- demo 데이터와 live 데이터 구분
- 변경 전후 diff

관련 파일:

```text
core/public_api_clients.py
core/policy_ingestion.py
core/policy_provenance.py
core/policy_store.py
```

이를 통해 기관은 정책 정보가 어디서 왔는지 확인할 수 있고, 정책이 바뀌었을 때 영향을 받는 청년을 다시 찾을 수 있습니다.

### 7.7 RAG 기반 정책 근거 검색

RAG는 AI가 답을 지어내지 않도록, 먼저 정책 문서나 카탈로그에서 근거를 찾고 그 근거를 바탕으로 답하게 하는 방식입니다.

LifePass에서는 다음 흐름으로 사용됩니다.

```text
사용자 질문
→ 관련 정책 문서 검색
→ 룰엔진 판정 결과와 결합
→ 쉬운 상담 답변 생성
```

예시 질문:

```text
실업급여가 45일 뒤 끝나면 무엇을 준비해야 하나요?
```

시스템은 실업급여 종료 후 가능한 제도, 신청 서류, 신청 시점 관련 근거를 찾고, 상담사가 설명하기 쉬운 문장으로 정리합니다.

### 7.8 신청 case와 운영자 검토

LifePass는 추천에서 끝나지 않습니다.  
실제 신청 관리 흐름까지 이어집니다.

지원하는 상태:

```text
draft
submitted
needs_human_review
approved
rejected
sent_to_agency
closed
```

관련 파일:

```text
core/application_review.py
```

기관 상담사는 신청 case를 만들고, 검토가 필요한 사례를 따로 모아볼 수 있습니다.

### 7.9 알림 outbox

마감 알림이나 상태 변경 알림을 바로 보내지 않고, 먼저 outbox에 저장합니다.

Outbox는 쉽게 말해 **나중에 처리해야 할 일을 쌓아두는 목록**입니다.

예시:

```text
실업급여 종료 D-30 알림
월세 지원 신청 마감 D-7 알림
서류 미제출 알림
상담사 검토 요청
정책 변경 후 재판정 알림
```

관련 파일:

```text
core/notification_delivery.py
core/v5_event_mesh.py
```

실서비스에서는 이 구조에 카카오 알림톡, 이메일, SMS 등을 연결할 수 있습니다.

### 7.10 개인정보 보호와 감사 로그

복지 플랫폼은 민감한 정보를 다룹니다.

예시:

- 소득
- 고용 상태
- 실업급여 수급 여부
- 거주지
- 월세
- 가구원 수

그래서 LifePass는 다음 기능을 제공합니다.

- 개인정보 동의 기록
- 접근 목적 기록
- 누가 어떤 정보를 봤는지 기록
- 마스킹
- 권한 기반 접근 제어
- 감사 로그

관련 파일:

```text
core/privacy_audit.py
core/v5_privacy_security.py
```

기관용 서비스에서는 이 기능이 매우 중요합니다.

## 8. 실시간 이벤트는 왜 필요한가

LifePass에서 말하는 실시간 이벤트는 채팅처럼 0.1초 단위 반응을 뜻하지 않습니다.

여기서의 이벤트는 다음 의미입니다.

> 사용자의 상태, 신청 마감, 정책 조건이 바뀌었을 때 시스템이 후속 작업을 자동으로 이어가게 하는 신호

예시 이벤트:

| 이벤트 | 발생 상황 | 후속 작업 |
|---|---|---|
| `profile.updated` | 소득, 지역, 고용 상태 변경 | 자격 재판정 |
| `benefit.expiring` | 실업급여 종료 임박 | 대체 제도 추천 |
| `application.deadline_approaching` | 신청 마감 임박 | 알림 생성 |
| `policy.updated` | 정책 조건 변경 | 영향받는 청년 재계산 |
| `human_review.required` | 자동 판단이 위험한 사례 | 상담사 검토 큐 생성 |
| `notification.requested` | 사용자에게 알려야 하는 상황 | 알림 outbox 저장 |

즉, 이벤트 구조는 여러 청년을 관리하는 기관이 중요한 시점을 놓치지 않도록 돕기 위한 기능입니다.

## 9. DB는 어떻게 쓰이는가

LifePass는 로컬 실행에서는 SQLite fallback을 사용할 수 있고, 운영 환경에서는 PostgreSQL을 메인 DB로 사용하도록 설계되어 있습니다.

### 9.1 SQLite

SQLite는 로컬 개발과 빠른 시연용입니다.

특징:

- 별도 설치가 거의 필요 없습니다.
- Python 기본 `sqlite3` 모듈로 사용할 수 있습니다.
- 로컬에서 가볍게 실행할 때 적합합니다.
- 실서비스 운영용 메인 DB로는 적합하지 않습니다.

### 9.2 PostgreSQL

PostgreSQL은 기관용 운영 환경의 메인 DB입니다.

저장 대상:

- 기관 정보
- 청년 프로필 기록
- 정책 카탈로그
- 정책 문서 조각
- Agent 실행 기록
- 자격 판정 단계 기록
- 신청 workflow
- 알림 outbox
- 개인정보 접근 로그
- 감사 로그

관련 SQL 파일:

```text
infra/postgres/init.sql
```

주요 테이블:

```text
tenants
profile_snapshots
policy_catalog
policy_chunks
agent_runs
agent_steps
event_outbox
application_workflows
audit_logs
```

### 9.3 pgvector

pgvector는 PostgreSQL 안에서 정책 문서의 의미 검색을 하기 위한 기능입니다.

예를 들어 사용자가 “월세 지원”이라고 물어봤을 때, 문서에 “주거비 지원”이라고 적혀 있어도 의미가 비슷한 문서를 찾을 수 있게 해줍니다.

### 9.4 Redis

Redis는 알림, 이벤트, 후속 작업을 빠르게 처리하기 위한 큐 구조로 사용할 수 있습니다.

예시 흐름:

```text
event_outbox에 이벤트 저장
→ Redis queue로 전달
→ worker가 읽어서 처리
→ 알림 발송 또는 재판정 수행
```

현재 프로젝트는 Redis-ready 구조를 갖고 있으며, 실서비스 단계에서는 실제 worker와 알림 발송기를 연결할 수 있습니다.

기관용 운영 구조를 확인하려면 Docker Compose 실행을 권장합니다.

```bash
cd lifepass

```

기본 접속 주소:

```text
Streamlit 화면: http://localhost:8503
```

```bash
docker compose ps
```

```bash
docker compose logs -f lifepass-ui
docker compose logs -f lifepass-api
```

종료:

```bash
docker compose down
```

```bash
docker compose down -v
```

## 11. `.env` 설정

프로젝트 루트에 `.env` 파일을 만들고 아래처럼 설정합니다.

```env
LIFEPASS_DATABASE_URL=postgresql://lifepass:lifepass@postgres:5432/lifepass
LIFEPASS_REDIS_URL=redis://redis:6379/0
LIFEPASS_ENABLE_PGVECTOR=1
LIFEPASS_TENANT_KEY=seoul-demo
LIFEPASS_RUN_MODE=competition

PUBLIC_POLICY_API_TIMEOUT=8
PUBLIC_POLICY_API_USE_CACHE=1

LIFEPASS_EMBEDDING_PROVIDER=local_hash
LIFEPASS_EMBEDDING_MODEL=local-hash-ko-384
LIFEPASS_LLM_PROVIDER=template
LIFEPASS_LLM_MODEL=gpt-4o-mini
LIFEPASS_OPENAI_TIMEOUT=30
LIFEPASS_LLM_MAX_TOKENS=900
# OPENAI_API_KEY=your_openai_api_key_here
```

기본 설정은 API 키가 없어도 동작하는 로컬 모드입니다.

OpenAI 기반 embedding 또는 LLM을 사용할 때만 아래처럼 바꿉니다.

```env
LIFEPASS_EMBEDDING_PROVIDER=openai
LIFEPASS_EMBEDDING_MODEL=text-embedding-3-small
LIFEPASS_LLM_PROVIDER=openai
LIFEPASS_LLM_MODEL=gpt-4o-mini
OPENAI_API_KEY=your_openai_api_key_here
```

보안 주의:

- 실제 API 키가 들어간 `.env`는 GitHub에 올리면 안 됩니다.
- 대회 제출 zip에도 `.env`를 넣지 않는 것이 안전합니다.
- 팀원에게는 `.env.example`만 공유하고, 실제 키는 각자 따로 설정하게 하는 것이 좋습니다.

```text
7. 정책 변경 영향 시뮬레이션 확인
8. 신청 case와 운영자 검토 큐 확인
9. 알림 outbox 확인
10. 개인정보 접근 기록과 감사 로그 확인
```

## 14. FastAPI 주요 주소

Docker Compose 실행 후 아래 주소에서 API 문서를 볼 수 있습니다.

```text
http://localhost:8002/docs
```

대표 API:

| API | 역할 |
|---|---|
| `POST /api/v1/analyze` | 한 명의 청년에 대해 자격 판정과 혜택 조합을 계산합니다. |
| `POST /api/v1/batch/analyze` | CSV로 여러 청년을 한 번에 분석합니다. |
| `POST /api/v1/rag/ask` | 정책 근거를 찾아 상담 답변을 만듭니다. |
| `POST /api/v1/policy/digital-twin` | 정책이 바뀌었을 때 영향을 미리 계산합니다. |
| `POST /api/v1/policies/sync-all` | 정책 데이터를 가져오고 저장합니다. |
| `GET /api/v1/policies/sync-runs` | 정책 동기화 이력을 확인합니다. |
| `POST /api/v1/auth/login` | 로그인 토큰을 발급합니다. |

## 17. 기술 용어 쉬운 설명

| 용어 | 쉬운 설명 |
|---|---|
| LLM | ChatGPT 같은 큰 언어 모델입니다. 이 프로젝트에서는 설명문을 만드는 보조 역할입니다. |
| RAG | 답을 그냥 지어내지 않고, 문서에서 근거를 찾아 답하게 하는 방식입니다. |
| rule engine | 정책 조건을 하나씩 검사해 가능/불가능을 판정하는 코드입니다. |
| optimizer | 여러 혜택 중 실제로 좋은 조합을 고르는 계산 로직입니다. |
| policy digital twin | 정책을 실제로 바꾸기 전에 가상으로 바꿔 보고 영향을 미리 계산하는 기능입니다. |
| provenance | 데이터가 어디서 왔는지, 언제 가져왔는지 남기는 기록입니다. |
| diff | 바뀌기 전과 바뀐 후의 차이입니다. |
| outbox | 바로 보내지 않고, 나중에 처리할 작업을 쌓아두는 목록입니다. |
| pgvector | PostgreSQL에서 문서 의미 검색을 하기 위한 확장 기능입니다. |
| Redis | 알림이나 이벤트 같은 작업을 빠르게 처리하기 위한 대기열로 쓸 수 있는 프로그램입니다. |
| audit log | 누가, 언제, 어떤 정보를 봤는지 남기는 기록입니다. |
| human review | 자동 판단이 위험하거나 애매한 사례를 사람이 검토하는 과정입니다. |

## 20. 요약

LifePass는 청년 개인을 최종 수혜자로 하되, 실제 도입 고객은 청년센터·지자체·대학·복지기관인 B2B2C 복지 운영 플랫폼입니다. 기관은 여러 청년의 상담 데이터나 CSV 명단을 입력하고, 시스템은 자격 판정, 복지절벽 위험 감지, 신청 우선순위 산출, 상담사 검토 큐, 알림, 개인정보 감사 로그까지 운영 흐름으로 연결합니다. 자격 판단은 LLM이 아니라 재현 가능한 규칙 기반 판정 코드가 수행하며, LLM은 검색된 정책 근거와 판정 결과를 쉬운 상담 문장으로 설명하는 역할로 제한됩니다.
